# ADR 0015: Pairing a counter with a short one-time code

Status: accepted (24 Oct 2026). Amends locked rules 3 and 6 in CLAUDE.md (one more public path, one more global lookup), the same way ADR 0007 did.

## Context
A counter had to be given the whole device credential (`tzd.<tenant>.<device>.<secret>`, about 130 characters) by hand. That is
hard to read out, easy to mistype, and the owner needed the API (`curl`) to get it. Standard POS products (Square device codes,
Shopify POS pairing) use a short code the owner reads off their screen and the counter types once.

## Decision
- **Owner side**: `POST /v1/identity/device-pairings` (`DEVICE_MANAGE`, owner session or device + staff) takes a store and an optional
  label and returns a code shown as `ABCD-EFGH`, valid for 10 minutes (`tarazu.pairing.ttl-minutes`), usable once.
- **Counter side**: `POST /v1/pairing/redeem` (public) takes the code, a **device id chosen by the counter** and a **256-bit secret
  generated by the counter** (43 base64url characters). The server creates the device exactly as `PUT /v1/identity/devices/{id}`
  does (only the SHA-256 of the secret is stored, `registered_by` is the owner who made the code), marks the pairing used, writes
  `device.paired` to the audit log and answers with the token `tzd.<tenant>.<device>.<secret>` plus tenant, store and label.
- **Retries are safe (rule 5)**: if the response is lost, the counter repeats the call with the same code, device id and secret and
  gets 200 with the same body, never a second device. Anyone presenting a used code with other values gets 409 `pairing_used`.
  The counter keeps its pending attempt until the server answers for good. Because the counter generated the secret, the server
  never has to keep or re-derive it.
- **Code**: 8 characters from a 32-character alphabet without 0/O/1/I (40 bits), case, spaces and dashes ignored.
- **Rule 3 amendment**: a code has to lead to a tenant before any tenant is known. `pairing_directory` (code hash, tenant id,
  pairing id, expiry) has no tenant_id RLS and **no privileges for the API role**; the only access is three `SECURITY DEFINER`
  functions with a pinned search_path (`pairing_register` acts only on the bound tenant, `pairing_lookup` is the one cross-tenant
  read and never returns an expired code, `otp_throttle_peek` reads a throttle bucket). Everything else (store, label, creator,
  expiry, state) is in `device_pairing`, a normal tenant table with RLS and composite foreign keys. `SchemaGuardIT` enforces both.
- **Rule 6 amendment**: `/v1/pairing/redeem` is the seventh path in `PublicPaths` (exact match). It takes only the one-time code.
  `FailClosedIT` proves every other `/v1` endpoint is still 401.
- **Guessing**: the table holds only `HMAC(pepper, code)` (the same pepper as OTP, `OTP_PEPPER`, 503 `pairing_not_configured`
  when unset). A wrong, unknown or expired code is one answer, 404 `pairing_invalid`. Because a wrong guess maps to no row there
  is nothing per code to count, so wrong or already-used attempts are counted in a **deployment-wide** budget
  (`tarazu.pairing.max-failures` per `tarazu.pairing.window-minutes`, default 30 per 10 minutes, counted over the current and
  previous window); when it is spent, redemption answers 429 until it clears. The check, the attempt and the count run in one
  transaction behind an advisory lock, so a parallel burst cannot overshoot the budget, and a counted failure is committed even
  though the request fails. Input that cannot be a code (wrong length or characters) is refused without spending budget. Per-IP limiting is left to the edge (ADR 0004).

## Why this is safe enough
An attacker needs a live code. With N codes outstanding and at most 30 guesses per window the chance per window is about
N x 30 / 2^40 (for 100 outstanding codes, about 3 in 1e9), a code lives 10 minutes, and the owner sees `device.paired` in the audit
log and can revoke the device at once (ADR 0004). A device token stays the long-lived credential; the code only mints it.

## Consequences
- The deployment-wide budget means someone who floods wrong codes can pause pairing for everyone for a window. That is a
  nuisance, not a breach, and it does not touch billing or sync (devices already paired are unaffected).
- Operators need `OTP_PEPPER` set (already required for OTP).
- A QR carrying the code and server URL, and the owner screen that shows the code, are separate slices. This ADR ships the
  API, the contract and the counter's Setup screen; until the owner screen exists the code is made with the API.
- The device token still sits in `localStorage` (see the TODOs in `sync/config.ts`); pairing does not change that.
